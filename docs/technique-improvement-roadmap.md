# План улучшения прохождения техник

Цель: сделать упражнения понятнее с первого прочтения, короче до первого действия и полезнее для конкретного запроса. План рассчитан на текущий Android-сценарий, каталог локализованного контента и чатовые протоколы. Визуальный стиль, экраны, XAML и навигация не меняются; улучшения выполняются в текстах, правилах выбора, состоянии протокола и тестах.

## P0 — безопасность и правильный выбор

1. [ ] **Инвентаризировать все техники.** Составить таблицу `TechniqueId → цель → подходящие ситуации → ограничения → локаль → шаги → завершение`; критерий — все элементы `TechniqueId` имеют запись, необработанных идентификаторов нет.
2. [ ] **Провести клиническое ревью содержания.** Проверить инструкции, противопоказания/осторожность, прекращение упражнения при ухудшении и кризисные переходы; не добавлять обещания лечения и не заменять профессиональную помощь.
3. [ ] **Стандартизировать карточку техники в модели контента.** Для каждой техники хранить внутренне: цель, ориентировочное время, подготовку, шаги, ожидаемый сигнал завершения, вариант «пропустить/остановить» и отметку ревью. Не вводить новые визуальные элементы.
4. [ ] **Проверить соответствие рекомендации запросу.** Для каждой пары эмоция/ситуация/напряжение определить подходящие техники, неподходящие варианты и случаи, когда лучше пока не предлагать практику; пороги и кризисные правила — только после клинического ревью. Инженерная часть продолжена 2026-11-03: рекомендации расширены для зацикленных мыслей, телесного напряжения и обиды; клиническое ревью остаётся открытым.
5. [ ] **Проверить безопасность дыхательных и телесных практик.** Добавить reviewed-сценарии для паники, головокружения, боли, травматических воспоминаний и отказа от фокусировки на теле; при неуместности давать нейтральный выход или прекращать практику.
6. [ ] **Проверить языковую полноту каталога.** Сверить каждый ID во всех поддерживаемых языках; отсутствие перевода должно явно попадать в отчёт сборки, а русский текст — пройти редакторскую проверку.

## P1 — ясность и скорость прохождения

7. [ ] **Переписать первое сообщение каждой техники.** В одном коротком блоке сообщать, что предлагается сделать, зачем и сколько примерно займёт; убрать жаргон, длинные вступления и повторное объяснение одной мысли.
8. [ ] **Ограничить шаг одной задачей.** Один ход протокола — одно действие или один вопрос; критерий — автотесты запрещают несколько инструкций/вопросов в одном шаге для всех guided-протоколов.
9. [ ] **Уточнить переходы между шагами.** Перед следующим шагом кратко отразить ответ человека и объяснить связь перехода; если ответ не относится к вопросу, не терять его и не перескакивать автоматически.
10. [ ] **Добавить ясные ориентиры времени без давления.** Указать примерную длительность и возможность закончить раньше; фактическую длительность измерять в пилоте, не обещать фиксированный результат.
11. [ ] **Сделать короткий маршрут основным.** Для упражнений с несколькими этапами определить минимально полезный путь и необязательное углубление через уже существующие варианты ответа; не требовать полного прохождения.
12. [ ] **Поддержать «пропустить», «пауза» и «стоп» на каждом шаге.** Проверить RU/EN формулировки и краткие ответы; остановка не должна повторно предлагать то же упражнение в ближайших ходах.
13. [ ] **Упростить возврат после перезапуска.** При восстановлении протокола сказать, на каком шаге остановились, и дать продолжить либо завершить; не повторять уже пройденные вопросы.
14. [ ] **Сделать завершение конкретным и коротким.** Подвести итог того, что человек сделал, предложить одну нейтральную проверку «стало ли легче/без изменений/хуже» и следующий вариант по ответу; не объявлять технику успешной за пользователя.

## P2 — адаптация и проверяемая эффективность

15. [ ] **Добавить обработку «не помогло» и «стало хуже».** Не обвинять пользователя и не настаивать; прекратить текущий маршрут, предложить безопасный следующий шаг из утверждённого набора и проверить кризисный маршрут.
16. [ ] **Учитывать предпочтения формата.** Запоминать только явные предпочтения (короче, без дыхания, без закрытых глаз и т. п.), давать возможность изменить их и удалять вместе с памятью пользователя.
17. [ ] **Не повторять неудачную практику автоматически.** Использовать явный недавний feedback; после отказа/ухудшения предлагать альтернативу только с согласия, а прошлую рекомендацию не считать эффективной по одному факту завершения.
18. [ ] **Собрать диалоговые сценарии для каждой техники.** Покрыть начало, непонимание, короткий/не по теме ответ, пропуск, остановку, ухудшение, перезапуск, завершение и кризисное прерывание на русском и английском.
19. [ ] **Ввести eval ясности инструкции.** Независимые участники после чтения своими словами объясняют первый шаг и критерий завершения; метрики — доля правильного понимания, запросы на повтор, время до первого действия и доля прерванных сценариев.
20. [ ] **Измерять полезность без клинических заявлений.** До/после спрашивать субъективную оценку состояния и полезности только при согласии; отдельно считать «помогло / без изменений / хуже / пропустил», не выдавать это за лечение или доказательство эффективности.
21. [ ] **Добавить локальный quality gate техник.** CI проверяет полноту языков, длину инструкций, валидность переходов, поддержку стоп/пропуска и regressions. Логи и отчёты не содержат пользовательских сообщений.

## Definition of done

- Ни один экран, визуальный стиль и навигация не изменены.
- Все техники покрыты каталогом, переводами и сценарными тестами; опасные/клинические формулировки прошли профильное ревью.
- Быстрота подтверждена временем до первого действия и временем прохождения, а понятность — независимой проверкой понимания. До пилота числовые улучшения не заявляются.
- Завершение упражнения само по себе не считается признаком улучшения состояния.
